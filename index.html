01 · LUIS ALEJANDRO BRAVO BELLO

Introducción e identificación

Durante el desarrollo de software cambian los requisitos, documentos, modelos, código y pruebas. La Administración de la Configuración del Software (ACS) organiza estos productos y sus modificaciones para mantener la coherencia del proyecto.

Sin esta coordinación, un equipo podría utilizar código actualizado junto con requisitos o pruebas que ya no corresponden a su comportamiento. La ACS ayuda a reconocer qué elementos forman una entrega y cuáles deben revisarse cuando ocurre un cambio.

Los cuatro objetivos de ACS

  • Identificar los elementos

    Reconocer y nombrar los productos que forman la configuración del software.

  • Administrar los cambios

    Organizar las modificaciones y considerar sus efectos sobre otros productos.

  • Construir distintas versiones

    Reunir los elementos y versiones adecuados para cada entrega del sistema.

  • Conservar la calidad

    Mantener la consistencia y el funcionamiento esperado mientras el software evoluciona.

EL PROCESO ACS

Las cinco tareas
del proceso

Del reconocimiento de un elemento al registro de sus cambios: cada tarea aporta una forma de conservar el orden.

  1. Identificación

    Nombrar, describir y organizar los elementos y sus relaciones.

  2. Control de versión

    Administrar las versiones de los productos que componen el sistema.

  3. Control de cambio

    Evaluar, autorizar y dar seguimiento a las modificaciones.

  4. Auditoría de configuración

    Verificar que lo realizado corresponde a lo aprobado y cumple los procedimientos establecidos.

  5. Reporte de estado

    Registrar y comunicar la situación de los elementos y sus cambios.

Estas tareas se complementan durante la vida de cada elemento. No representan una secuencia rígida: un objeto nuevo necesita identificación, pero si no recibe solicitudes de modificación, el control de cambio puede no aplicarse en ese momento.

Ítems y objetos de configuración

Un ítem de configuración del software (ICS) es un producto de trabajo, o una parte de él, que se identifica y administra dentro del proyecto. Puede ser un requisito, un modelo de diseño, un componente o un conjunto de pruebas.

Objeto básico

Una unidad de información creada durante el análisis, diseño, código o pruebas. Por ejemplo, un requisito específico o el código de un componente.

Objeto agregado

Una colección identificada de objetos básicos y otros agregados. Una especificación de diseño puede reunir modelos de datos, arquitectura y componentes.

Características de cada objeto

  • Nombre: lo identifica sin ambigüedad.
  • Descripción: indica su tipo, proyecto e información de versión o cambio.
  • Recursos: entidades que utiliza, procesa o referencia, como funciones, variables y tipos de datos.
  • Realización: referencia a la unidad de texto de un objeto básico. En un agregado es nula.

Relaciones e impacto de los cambios

Una relación «parte de» establece una jerarquía: un requisito pertenece a una especificación de requisitos. Las interrelaciones conectan objetos de distintas partes del proyecto, como ese requisito, el código que lo implementa y las pruebas que lo verifican.

Mantener estas relaciones permite reconocer qué otros productos podrían verse afectados por una modificación y necesitan revisión.

Línea de referencia

Es un producto o conjunto de productos revisados y aprobados que sirve como base para continuar el desarrollo. Antes de establecerla, los objetos pueden cambiar con mayor libertad; después, sus modificaciones siguen el procedimiento de control de cambio establecido.

La línea de referencia no impide que el software evolucione. Proporciona una base conocida para evaluar las modificaciones. Un commit puede señalar esa base, pero por sí solo no demuestra que haya sido revisada y aprobada.

Ejemplo: préstamos de biblioteca

REQ-01 · Requisito: cada estudiante puede tener hasta tres préstamos activos.

COD-Prestamos · Código: permite un nuevo préstamo si prestamosActivos < 3.

PRU-Prestamos · Pruebas: con dos préstamos permite otro; con tres lo rechaza.

Si el límite cambia a cinco, se actualizan el requisito, el código y las pruebas.

02 · ANDREA VALECILLOS

Control de versión y cambio

A medida que un sistema de software evoluciona, se generan múltiples versiones de sus componentes. El control de versión combina procedimientos y herramientas para administrar estos objetos de manera ordenada, evitando el caos que producen las modificaciones simultáneas y descontroladas.

Capacidades de un sistema de control de versión

Un sistema robusto integra o se conecta directamente con cuatro funciones fundamentales:

  • Base de datos del proyecto (repositorio): Almacena de forma centralizada todos los objetos de configuración relevantes.
  • Administración de versiones: Almacena todas las versiones de un objeto o permite reconstruir cualquier versión utilizando las diferencias respecto a las pasadas.
  • Facilidad de elaboración: Permite recopilar los objetos de configuración correctos para construir una versión específica del software.
  • Rastreador de conflictos (o de errores): Facilita al equipo registrar y seguir el estado de los conflictos e inconvenientes asociados con cada objeto.

Conjuntos de cambios y modelo del sistema

Algunos sistemas utilizan un conjunto de cambios (*change set*), que recopila todas las modificaciones realizadas en relación con una configuración de referencia para crear una versión específica. Este concepto captura los archivos modificados, la razón del cambio, quién lo hizo y cuándo.

Para aplicar estos conjuntos de manera estructurada se emplea un modelo del sistema, el cual contiene una plantilla con la jerarquía de componentes y el orden de construcción, las reglas de construcción y las reglas de verificación.

Herramienta de referencia: El Sistema de Versiones Concurrentes (SVC / CVS)

Diseñado originalmente para código fuente pero útil para archivos de texto, el SVC establece un repositorio simple y almacena versiones sucesivas guardando únicamente las diferencias (*deltas*) entre archivos.

Para proteger el trabajo en equipo, el SVC aísla a los desarrolladores asignando directorios separados y combina los cambios compatibles al integrar el trabajo. Si existen modificaciones incompatibles, se producen conflictos que los desarrolladores deben resolver antes de completar la integración. Nota importante: El SVC no es un sistema de construcción ni implementa por sí solo un proceso formal de control de cambios; necesita integrarse con herramientas externas como Makefile.

Control de cambio

El control de cambio representa un acto de equilibrio constante: demasiada burocracia desalienta el trabajo creativo y enlentece el progreso, mientras que la falta de control conduce rápidamente al caos y a fallas críticas en el producto.

Para proyectos grandes y visibles, se combinan procedimientos humanos y herramientas automatizadas siguiendo un flujo riguroso:

  1. Petición y Evaluación

    Se reconoce la necesidad del cambio y el usuario envía una petición. El desarrollador la evalúa considerando su mérito técnico, efectos colaterales e impacto global.

  2. Reporte y Decisión (ACC)

    Los resultados se documentan en un reporte de cambio. La Autoridad de Control de Cambio (ACC) (que puede ser el gerente o un comité multidisciplinario) decide si se aprueba, se rechaza o se pone en fila.

  3. Orden de Cambio de Ingeniería (OCI)

    Si se aprueba, se genera una OCI que detalla el cambio a realizar, restricciones y criterios de revisión.

  4. Implementación y Sincronización

    Se asigna a los desarrolladores, se extraen los objetos y se efectúan los cambios aplicando control de acceso (qué ingenieros pueden modificar un objeto) y control de sincronización (para evitar que cambios paralelos se sobrescriban).

  5. Verificación y Distribución

    Se audita el cambio, se restablece la línea de referencia para pruebas, se promueve la inclusión en la nueva versión del software y se distribuye.

Niveles de control de cambio

Control informal

Se aplica antes de que un objeto alcance una línea de referencia. El desarrollador realiza cambios justificados siempre que no afecten el sistema global.

Control a nivel de proyecto

Se activa tras establecer una línea de referencia inicial. Requiere la aprobación del gerente de proyecto para cambios locales o de la ACC si impacta otros componentes.

Control formal

Se instituye cuando el software ya ha sido liberado a los clientes, siguiendo estrictamente el proceso completo de peticiones, reportes y OCI.

Ejemplo práctico de control de cambios en el equipo

Situación: Durante el desarrollo de la página web del proyecto, el equipo detecta la necesidad de modificar los estilos CSS globales para mejorar la visualización en teléfonos móviles.

Aplicación del proceso: Andrea redacta la petición de cambio, la somete a revisión con el equipo (actuando como ACC de nivel de proyecto), genera una OCI interna para modificar exclusivamente el archivo assets/style.css en su rama de trabajo, realiza una auditoría técnica del resultado y efectúa el merge hacia la rama principal sin afectar los contenidos de HTML creados por Luis y Dubenny.
